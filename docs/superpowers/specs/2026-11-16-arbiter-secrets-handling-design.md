# Arbiter Hub — Secret Handling Design (Demo + Production)

Date: 2026-11-16
Status: Approved for planning
Related: build #17045 triage, commit `2f6626a`, `poc/RESULTS.md`

## Problem

The bootc Arbiter Server firstboot writes application secrets into systemd unit
files and passes one on a container command line. Three leaks, all observed or
directly implied by #17045:

1. `ARBITER_DATABASE_URL` and `ARBITER_LOCAL_ADMIN_PASSWORD` are emitted as
   `Environment=` in `/etc/containers/systemd/arbiter-hub-api.container.d/config.conf`.
   systemd exposes unit environment through `systemctl cat/show`, and the CI
   console already captured the DB password through an `ExecStart=` dump.
2. The drop-in directory is written with the process umask, so the files are
   mode 0644 — any local user can read both secrets.
3. The Alembic migration passes the full DSN, including the password, as
   `podman run -e ALEMBIC_DB_URL=...`; it is visible in `ps` and in the
   firstboot log.

Two secondary defects:

4. `podman secret arbiter-hub-db-password` is created and never referenced by
   the drop-in path (`deploy/quadlet/*.container` reference it, the drop-in
   overrides it with plaintext).
5. Passwords are regenerated by `openssl rand` whenever the variable is unset.
   Re-running firstboot therefore rotates the DB password without rotating the
   Postgres role, locking the API out of an already-initialized data volume.

## Goals

- One code path for demo and production. Only the *source* of the secret differs.
- Secrets are never in git, never in systemd unit files, never on a command
  line, never in stdout.
- Re-running firstboot is idempotent: existing secrets are reused.
- Production fails closed when no secret source is configured.
- Demo keeps working with zero operator input.

## Non-goals

- Replacing IPA/IdM credential handling (`IPA_ADMIN_PASSWORD`) — that is lab
  infrastructure, addressed separately in the demo metadata.
- Reworking Keylime/cosign key material (already file-based).
- Secret rotation after install.

## Design

### Capture point

Secrets live as **files**. The container engine mounts them; the application
reads them itself.

- Quadlet: `Secret=<name>,type=mount,target=<field_name>` → `/run/secrets/<field_name>`
- App: `pydantic-settings` `secrets_dir=/run/secrets` reads a field from a file
  of the same name with no extra code.
- Podman secret names: `arbiter-hub-db-password` (target `db_password`),
  `arbiter-hub-admin-password` (target `local_admin_password`).

Env vars remain supported for non-secret configuration and for the explicit
`ARBITER_DATABASE_URL` override (backwards compatibility with existing
deployments and the test suite).

### DSN assembly moves into the application

`server/db_url.py` owns one function:

```python
def build_dsn(password: str, user="arbiter", host="arbiter-hub-db",
              port=5432, database="arbiter") -> str
```

It percent-encodes the password itself. `settings.dsn` returns
`database_url` when set, otherwise `build_dsn(db_password)`. Alembic uses the
same function via `ALEMBIC_DB_PASSWORD` + `ALEMBIC_DB_HOST`, so firstboot never
constructs a URL in bash. This removes the URL-encoding bug class that produced
`2f6626a` bug 2, and makes it unit-testable.

### Generation and idempotency

`server-firstboot.sh` gets `ensure_podman_secret(name)`:

```bash
ensure_podman_secret() {
    podman secret inspect "$1" >/dev/null 2>&1 && return 0
    openssl rand -base64 "${2}" | podman secret create "$1" -
}
```

Behavior: if the secret exists, reuse it and never regenerate the value. If it
does not exist, generate one and create it. The DB role password and the podman
secret are initialized together by the same Postgres first-init, so they cannot
drift.

All secret-touching files are created under `umask 077`; drop-ins are
explicitly `chmod 600`.

### Deployment modes

`ARBITER_DEPLOYMENT_MODE` — `demo` | `production`, default `production`.

| Concern | demo | production |
|---|---|---|
| DB password source | generated at firstboot if absent | pre-sealed in `/etc/arbiter/secrets/*.cred` (systemd-creds, TPM2/host key) |
| Admin password source | generated at firstboot if absent | pre-sealed, same mechanism |
| Local admin (`ARBITER_LOCAL_ADMIN_ENABLED`) | true | false unless `ARBITER_ALLOW_LOCAL_ADMIN=true` |
| Unknown default password (`Secret123!`) | allowed | refused at firstboot |
| No secret source available | generate | fail closed, exit 1 |

Sealed credentials are decrypted by firstboot into podman secrets:

```bash
systemd-creds decrypt --name="$name" --with-key=host+tpm2 \
    "/etc/arbiter/secrets/${name}.cred" - | podman secret create "$name" -
```

The seal step runs at image deployment time (kickstart/cloud-init/Ansible),
not at boot, and is documented in `deploy/bootc/production-secrets.md`.

### Postgres container

`registry.redhat.io/rhel10/postgresql-16` accepts a password only through
`POSTGRESQL_PASSWORD`. Quadlet `Secret=...,type=env,target=POSTGRESQL_PASSWORD`
is retained **for this container only**: podman injects the value into the
container environment at start and it does not appear in any host unit file.
The API never uses env secrets; it uses mounts.

### Demo path

The demo metadata (`idm-ci/metadata/infra/bootc-arbiter-server-fedora-44.yaml`)
sets `ARBITER_DEPLOYMENT_MODE=demo` and keeps only the IPA admin password in
the injected `server.env`. DB and admin passwords are generated per VM. The
demo IPA password remains a lab-only value and is explicitly marked as such;
it never reaches production because production mode refuses known demo values.

## Threat model

- Local unprivileged user on the hub: previously could read DB and admin
  passwords (0644 unit files). After: cannot; files are 0600 and values live in
  the podman secret store as root.
- Anyone with Jenkins build-log access: previously saw DB password and admin
  password in plaintext. After: no secret value is printed by firstboot; the
  only remaining demo secret is the IPA admin password, which is scoped to
  throwaway VMs.
- Root on the hub: can always read secrets. Production closes the at-rest gap by
  sealing with TPM2 (`--with-key=host+tpm2`), so a stolen disk does not yield
  credentials.

## Rollout

1. App changes first (backwards compatible: explicit URL still wins).
2. Quadlet + firstboot changes together (one image rebuild).
3. CI metadata marks `demo`.
4. Production sealing is opt-in and documented; it becomes mandatory when a
   customer deployment is onboarded.

## Review Findings (2026-11-16)

### Accepted exceptions

1. **Postgres `type=env` exception** — SCL `postgresql-16` has no `_FILE`
   support; `Secret=...,type=env,target=POSTGRESQL_PASSWORD` is retained for
   the DB container only. Podman injects at runtime; the value never appears in
   a host unit file. A wrapper entrypoint or alternate image would add
   complexity for marginal gain. Accepted as-is.

2. **EDA `hosts.yml` reads from `SECRETS_DIR`** — `ARBITER_SERVICE_PASSWORD`
   is replaced by `$(cat "${SECRETS_DIR}/local_admin_password")`. The file is
   `chmod 600`. Moving EDA auth to webhook-secret-only is a separate scope
   item.

3. **Production default (`ARBITER_DEPLOYMENT_MODE=production`)** — Fail-closed
   is correct. An unmodified demo image fails firstboot loudly, which means the
   CI metadata change (plan Task 6) must ship in the same image rebuild as the
   mode guard (plan Task 5). They are a hard dependency, not sequential
   nice-to-haves.

4. **Demo IPA password stays in git** — Scoped out (see Non-goals). Moving it
   requires a Jenkins credential-injection investigation that belongs in a
   separate plan.

### Bugs found in the implementation plan

**Bug A: `test_dsn_without_secrets_dir_does_not_raise` contradicts `build_dsn`.**
`db_password` defaults to `SecretStr("")`; when no `database_url` is set,
`Settings.dsn` calls `build_dsn("")`, which raises `ValueError` per spec.
The test expects success. Resolution: drop the test — the "no secrets, no URL"
case is an error, not a graceful default. Let the `ValueError` propagate.

**Bug B: `ensure_podman_secret` name/file mismatch.**
`ensure_secret_file` creates files named `db_password` and
`local_admin_password`, but `ensure_podman_secret` is called with podman
secret names (`arbiter-hub-db-password`, `arbiter-hub-admin-password`) and
reads `${SECRETS_DIR}/${name}` — a file that does not exist. Fix: add a
second argument for the source filename:

```bash
ensure_podman_secret() {
    local name="$1" file="$2"
    podman secret inspect "$name" >/dev/null 2>&1 && return 0
    podman secret create "$name" < "${SECRETS_DIR}/${file}"
}

ensure_podman_secret arbiter-hub-db-password db_password
ensure_podman_secret arbiter-hub-admin-password local_admin_password
```
